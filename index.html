New approach (April 2026): A community contribution from Tim suggests splitting CLAUDE.md into three focused files instead of one. Lighter on tokens, scales better on bigger projects. Both options available below. Read the tip in "Writing a Good CLAUDE.md" below for when to use which.

Splits your project into three focused files that never need archiving. Claude loads only what's relevant to the task.

CLAUDE.md Rules only

Stays tiny forever. Contains just the rules Claude must follow every session, plus an instruction to read CONTEXT.md and ROADMAP.md at session start.

CONTEXT.md Current state

A living snapshot of the project now. Tech stack, what's been built, current status, known issues. Rewritten in place when things change, never appended to. Grows with scope not time, so it plateaus once the project matures.

ROADMAP.md Forward plan

Future only. Upcoming phases, architectural commitments, locked-in decisions with dates. Never contaminated with current state so the two don't mix.

Paste this into Claude to create all three files:

prompt 
Create three files in the project root with this content:

- Read ROADMAP.md if the task relates to future plans or phases.
- Read RECENT.md if it exists, for conversation context from the last session.

### GitHub Safety
- Always commit working code before starting edits.
- If a change may break existing functionality, create a new branch.
- Write clear, descriptive commit messages.

### Preserve Functionality
- Do not remove or alter working features unless explicitly instructed.
- If a change risks regression, stop and explain before proceeding.

### Code Changes
- Keep changes incremental and well-commented.
- Highlight what was added, removed, or updated.

### Verification
- After edits, run tests or basic checks.
- Report any errors or warnings.

### CONTEXT.md Maintenance
- When something significant changes, update CONTEXT.md in place.
- Do not append a session log. Rewrite the affected sections instead.

### General
- Treat GitHub as the single source of truth.
- All steps must be safe, reversible, and transparent.

Stable Sessions over SSH

✨

Community contribution. A method for stopping Claude Code sessions dying when your connection drops. Not yet tested on our own setup, so treat it as a recommended approach to try rather than a guaranteed recipe. Requires a paid Replit plan (SSH is not on the free tier).

If you run Claude Code in Replit's browser Shell, the session often dies when the connection drops. The browser terminal is a thin client over a websocket, so a network blip, a backgrounded tab, or your laptop sleeping can tear it down and kill whatever was running. The fix: connect to the same Replit container from your own computer's terminal over SSH instead. Nothing moves off Replit, your code, database, secrets and runtime stay exactly where they are. You just reach the container through a far more stable connection that also survives the container hibernating.

Why not tmux? tmux is the usual tool for surviving disconnects, but on newer Replit Apps it conflicts with Claude Code's interface and is more trouble than it's worth. SSH solves it more completely and survives hibernation, which tmux cannot.

This key lets your computer prove who it is to Replit. You only do this once, the same key works for every Replit app on your account.

Step 1: Create the key (on your computer's Terminal)

bash, your computer
ssh-keygen -t ed25519 -f ~/.ssh/replit -q -N ""

If it asks "Overwrite?", you already have a key with that name, type n and reuse the existing one.

Step 2: Display the public key to copy it

bash, your computer
cat ~/.ssh/replit.pub

Copy the whole line starting with ssh-ed25519.

Step 3: Add the key to Replit (account-wide, once)

  • Open any Replit app, click the + button at the top, search for SSH
  • If SSH doesn't appear you're likely on a free plan, where it isn't available
  • In the SSH pane, open the Keys tab, click New SSH key
  • Give it a label (e.g. "my laptop"), paste the ssh-ed25519 line into the Key field, click Add SSH key

Step 4: Set up your SSH config (once)

Create and open the config file:

bash, your computer
mkdir -p ~/.ssh && chmod 700 ~/.ssh && touch ~/.ssh/config && chmod 600 ~/.ssh/config
nano ~/.ssh/config

Paste in exactly this block, then save with Ctrl+O, Enter, Ctrl+X:

~/.ssh/config
Host *.replit.dev
   Port 22
   IdentityFile ~/.ssh/replit
   StrictHostKeyChecking accept-new

Step 1: Connect the first time

  • Open the app in Replit so its container is running (give a sleeping app 20 to 30 seconds to wake)
  • In the app, open the SSH pane → Connect tab → Connect manually
  • Copy the whole command, it looks like ssh -i ~/.ssh/replit -p 22 USER@HOST.replit.dev
  • Paste it into your computer's Terminal and press Enter. First time you may get an authenticity prompt, type yes
  • You should land at ~/workspace$. Run ls to confirm you see your app's files

Harmless: you may see setlocale: cannot change locale lines. Cosmetic, ignore them.

Step 2: Save it as a one-word command

Typing the long command each time is tedious. Save it as an alias named after the app. Replace APPNAME with a lowercase name and paste the whole connect command you copied:

bash, your computer
echo 'alias APPNAME="PASTE_WHOLE_CONNECT_COMMAND"' >> ~/.zshrc
source ~/.zshrc

Example: echo 'alias reviseninja="ssh -i ~/.ssh/replit -p 22 USER@HOST.replit.dev"' >> ~/.zshrc. Keep the single quotes outside and double quotes inside exactly as shown. Don't trim any part of Replit's command.

Now you connect to that app just by typing its name. Add one alias line per app.

If an alias stops working later, Replit occasionally moves a container to a new address. Grab a fresh "Connect manually" command and update that one alias line. Your key never changes.

  • Open the app in Replit (wakes the container)
  • In your Terminal, type the app's alias and Enter
  • Start Claude Code:
bash, in the container
claude          # start fresh
claude -c       # resume your most recent conversation
claude --resume # pick a past conversation from a list
💡 Claude Code saves your conversation automatically and continuously inside the container, and the container persists between visits. So claude -c picks up exactly where you left off, no manual save needed. SSH, the GitHub token, and Claude Code's own login all persist per container, so opening a new terminal does not make you log in again.

Connecting solves stability. Separately, push your work to GitHub so you can recover if a container is ever rebuilt or wiped. The GitHub token is a different thing from the SSH key: the SSH key connects your computer to the container (account-wide), the GitHub token lets the container talk to GitHub (stored per container, so each app needs its own).

Set your git identity (per container)

bash, in the container
git config --global user.email "you@example.com"
git config --global user.name "Your Name"

Use the email verified on your GitHub account, or commits won't link to your profile.

Create a Personal Access Token

  • Go to github.com/settings/tokens → Generate new token (classic)
  • Name it clearly, set an expiry, tick the repo scope
  • Generate and copy it immediately (shown once, starts with ghp_)

Store it so you're only asked once

bash, in the container
git config --global credential.helper store

Then run any git command. When prompted, username is your GitHub username, password is the ghp_ token (not your account password). After that git saves it and never asks again in that container.

⚠️ Backup vs restore, keep these straight. Backup/checkpoint pushes your conversation and commits code to GitHub, safe to run anytime. Restore OVERWRITES the container's current sessions with the last backed-up copy, only run it after an actual wipe. Do NOT run restore when you open a session, the auto-saved history is already there, just connect and run claude -c.

Three steps, two copy-pastes. Your original CLAUDE.md is safely backed up on GitHub in Step 1, so you can git revert at any point if something looks wrong.

Step 1: Backup first Safety net

Commit your current CLAUDE.md to GitHub before anything else. This is your rollback point if anything goes wrong in Step 2.

bash , run in Replit Shell

git commit -m "chore: backup CLAUDE.md before three-file migration"

Step 2: Run the migration prompt One paste, Claude does the rest

Paste this into Claude. It reads your current CLAUDE.md, creates the three new files, archives your old Session Log, and shows you the final state before committing. If anything looks wrong you can roll back with git revert.

prompt 
Please migrate my project from the single CLAUDE.md setup to the three-file setup (CLAUDE.md + CONTEXT.md + ROADMAP.md). Do all of this in one go:

1. Read my current CLAUDE.md in full.

2. Create CONTEXT.md containing:
   - Project overview
   - Tech stack
   - Project structure (key folders)
   - Current status (in progress, last checkpoint, branch)
   - What's built so far
   - Pending tasks
   - Known issues
   - Any significant design decisions

3. Create ROADMAP.md containing:
   - Locked-in decisions (with dates where known)
   - Next phase
   - Future phases
   - Out of scope items

4. Move my existing Session Log into a new file called CLAUDE_ARCHIVE.md. Do NOT delete it.

5. Rewrite CLAUDE.md to contain only:
   - The rules section (keep all existing rules)
   - An instruction at the top telling you to read CONTEXT.md at session start, and to read ROADMAP.md if the task relates to future plans
   - An instruction to update CONTEXT.md in place when something significant changes (not append)

6. Once all four files are created, show me:
   - The file size of each file
   - A one-line summary of what ended up in each
   - Confirmation that nothing was deleted, only moved or rewritten

7. Do NOT run any git commands. I will review the files and commit them myself in Step 3.
Step 3: Review and commit Final

Open each file and check nothing important is missing. Your rules should all still be in CLAUDE.md. Your project history should be in CLAUDE_ARCHIVE.md. If anything looks wrong, run the rollback command at the bottom of this section. If everything looks good, commit all four files.

bash 
git add CLAUDE.md CONTEXT.md ROADMAP.md CLAUDE_ARCHIVE.md
git commit -m "feat: migrate to three-file Claude Code setup"
git push
Rollback (if anything looks wrong)

If Step 2 produced something you're not happy with, roll back to your Step 1 backup. This undoes everything.

bash 
git checkout CLAUDE.md
rm -f CONTEXT.md ROADMAP.md CLAUDE_ARCHIVE.md

Quick checkpoint (mid-session)

Lightweight save

Use this at any natural pause point during a session, after a feature, after a bug fix, whenever you'd want a safe rollback point. Takes seconds.

say to claude 
checkpoint

Claude runs the script which automatically:

  • Generates RECENT.md from the last 25 conversation turns
  • Warns you if any code files are newer than CONTEXT.md
  • Runs git add, commit and push in one shot
💡 The more often you checkpoint, the better. Each one is a safe rollback point and keeps RECENT.md fresh for next session.

Full end-of-day wrap-up

Checkpoint Script Community

Contributed by Tim from the community. Drop this script into your project root and typing checkpoint to Claude replaces the entire wrap-up prompt. One word does everything.

✅

Good news for Replit users: The script uses ~/workspace which is the standard Replit project path. It works out of the box across all Replit apps with no changes needed. (Confirmed by Tim across 4+ Replit projects.)

There are three commands you'll use day to day:

checkpoint Most used

Create a backup at any natural pause point. Type checkpoint "what you just did" to Claude. Claude runs the script which generates RECENT.md, warns if CONTEXT.md is stale, then commits and pushes everything to GitHub in one shot.

claude --resume Continue conversation

When you come back later and want to pick up the exact conversation. Start Claude Code fresh in the terminal, then run claude --resume. Good for short breaks or same-day continuation.

handoff Fresh session

When a conversation has got very long and Claude is slowing down, or you're starting a new day. Instead of resuming, type handoff to Claude. It starts a brand new session and bootstraps itself from CONTEXT.md and RECENT.md so you get a fast clean session without losing context.

Save this as claude-backup.sh in your project root. Works on Replit as-is, no path changes needed.

bash, claude-backup.sh 
#!/bin/bash
SESSION_DIR="$HOME/.claude/projects/$(echo "$HOME/workspace" | sed 's|/|-|g')"
BACKUP_FILE="$HOME/workspace/claude-session-backup.jsonl"
CONTEXT_FILE="$HOME/workspace/CONTEXT.md"
RECENT_FILE="$HOME/workspace/RECENT.md"
RECENT_TURNS=25

case "$1" in
  checkpoint)
    shift
    CURRENT=$(ls -t "$SESSION_DIR"/*.jsonl 2>/dev/null | head -1)
    if [ -z "$CURRENT" ]; then
      echo "No active session found."
      exit 1
    fi
    cp "$CURRENT" "$BACKUP_FILE"
    echo "Backed up: $(basename "$CURRENT") ($(du -h "$BACKUP_FILE" | cut -f1))"

    if jq -n -r --argjson n "$RECENT_TURNS" '
      [inputs
       | select(.type == "user" or .type == "assistant")
       | .message.content as $c
       | {
           role: .type,
           text: (
             if ($c | type) == "string" then $c
             elif ($c | type) == "array" then
               [$c[] | select(.type == "text") | .text] | join("\n")
             else "" end
           )
         }
       | select(.text | length > 0)
      ] as $all
      | ($all[-$n:]) as $tail
      | "# RECENT.md, auto-generated transcript tail\n\n"
        + "_Last \($tail | length) conversation turns from the most recent session._  \n"
        + "_Auto-overwritten on every checkpoint._\n\n"
        + "---\n\n"
        + ([$tail[]
            | (if .role == "user" then "## 👤 USER" else "## 🤖 CLAUDE" end)
              + "\n\n" + .text + "\n\n---\n\n"
          ] | join(""))
    ' "$CURRENT" > "$RECENT_FILE" 2>/dev/null && [ -s "$RECENT_FILE" ]; then
      echo "Wrote RECENT.md ($(wc -l < "$RECENT_FILE") lines)"
    else
      echo "WARNING: failed to write RECENT.md (jq missing or jsonl unparseable)"
    fi

    cd ~/workspace
    if [ -f "$CONTEXT_FILE" ]; then
      NEWEST_CODE=$(find app components lib middleware.ts next.config.ts 2>/dev/null \
        -type f \( -name '*.ts' -o -name '*.tsx' -o -name '*.js' -o -name '*.json' \) \
        -newer "$CONTEXT_FILE" -print -quit)
      if [ -n "$NEWEST_CODE" ]; then
        echo ""
        echo "WARNING: CONTEXT.md may be stale, code modified more recently."
        echo "  Ask Claude to refresh CONTEXT.md before checkpointing."
        echo ""
      fi
    else
      echo "WARNING: CONTEXT.md not found. Ask Claude to create one."
    fi

    if ! git diff --quiet || ! git diff --cached --quiet || [ -n "$(git ls-files --others --exclude-standard)" ]; then
      git add -A
      git commit -m "Checkpoint: $*" 2>/dev/null
      git push 2>/dev/null
      echo "Code committed and pushed."
    fi
    ;;
  handoff)
    if [ ! -f "$CONTEXT_FILE" ]; then
      echo "No CONTEXT.md found. Ask Claude to create one first."
      exit 1
    fi
    cat <<'EOF'
Please read ~/workspace/CONTEXT.md to get up to speed on this project, then
confirm in one or two sentences what you understand the current state to be
and what's outstanding. After that, we'll continue from where the previous
session left off.
EOF
    ;;
  restore)
    if [ ! -f "$BACKUP_FILE" ]; then
      echo "No backup found."
      exit 1
    fi
    mkdir -p "$SESSION_DIR"
    CURRENT=$(ls -t "$SESSION_DIR"/*.jsonl 2>/dev/null | head -1)
    if [ -n "$CURRENT" ]; then
      cp "$BACKUP_FILE" "$CURRENT"
      echo "Restored to: $(basename "$CURRENT")"
    else
      NEW_ID=$(uuidgen 2>/dev/null || cat /proc/sys/kernel/random/uuid)
      cp "$BACKUP_FILE" "$SESSION_DIR/${NEW_ID}.jsonl"
      echo "Restored as new session: ${NEW_ID}"
    fi
    echo "Run 'claude --resume' to continue."
    ;;
  *)
    echo "Usage:"
    echo "  $0 checkpoint \"description\"  - Backup + generate RECENT.md + commit + push"
    echo "  $0 handoff                    - Print bootstrap prompt for a fresh session"
    echo "  $0 restore                    - Restore the backed-up session file"
    ;;
esac

Writing a Good CLAUDE.md

The template gets you started but how you fill it in makes all the difference. A poorly written CLAUDE.md is almost as bad as not having one , Claude will follow vague rules vaguely. Here's what actually works.

The best rules are short, specific, and tell Claude what to do rather than what not to do.

✓ Good
markdown
- Always commit working code before starting any edits
- Use functional React components only , no class components
- Run `npm test` before every commit
- If a change risks breaking existing features, create a branch first
- Use /simplify after every code change before reporting back
✗ Too vague
markdown
- Be careful with the code
- Don't break things
- Write good code
- Be safe
Rules for Claude Always loaded

Short, direct instructions Claude must follow every session. Keep these to things that are genuinely always true , GitHub safety rules, commit conventions, never-do-this boundaries. If it only applies sometimes, put it in Project-Specific Rules instead.

Project Overview + Tech Stack Always loaded

Claude uses this to make better decisions. Be specific , "React 18 + Node.js + PostgreSQL + Tailwind" is more useful than "web app". List the key folders too so Claude knows where to look without asking.

Current Status + Pending Tasks Updated each session

This is the most valuable part for daily use. Keep it current. If you left a branch half-finished or hit a blocker, note it here. Claude uses this to pick up exactly where you left off without you having to re-explain context.

Session Log Updated each session

This is your history. Claude uses it to understand what changed and why. Keep entries concise , bullet points not paragraphs. Archive to CLAUDE_ARCHIVE.md when it gets over 30k characters or performance starts to dip.

Project-Specific Rules Most impactful section

This is where you teach Claude your stack and your preferences. API patterns, component conventions, which libraries to use for what, naming conventions, deployment notes. The more specific this is, the better every session gets. Add to it whenever Claude does something you have to correct.

  • Write rules the way you'd tell a new developer. If you wouldn't say it out loud to a colleague, it's probably too vague for Claude.
  • When Claude does something wrong, add a rule. The best CLAUDE.md files grow from real corrections. If you have to correct Claude twice, that's a rule.
  • Reference your skills in the rules. E.g. "Use /simplify after every code change" or "Use /debug before attempting any fix." This makes skills automatic.
  • Keep the rules section short. 10 sharp rules outperform 40 vague ones. Claude reads every rule every session , make each one count.
  • Put environment-specific stuff in Project-Specific Rules, not the main rules. Things like "we use Supabase not Firebase" belong there, not at the top.
  • Archive early, not when it breaks. Don't wait until Claude starts drifting. Archive logs at 25k characters rather than waiting for 30k.
  • Scope not time (for three-file setup): A session log grows with time, CONTEXT.md grows with scope. Time is unbounded, scope plateaus once the project matures. If you find CONTEXT.md still growing every session, you're probably appending instead of rewriting in place. (Credit: Tim, community contribution)

Common Mistakes

These aren't error messages , they're habits that quietly make Claude Code worse over time. Most people hit all of them in the first few weeks.

🚫 Not committing before starting edits
The single most common cause of lost work. Claude makes several changes, something breaks, and you have no safe state to roll back to. The GitHub safety rules in CLAUDE.md exist to stop this but only if you actually put them there. Make committing first a reflex.
🚫 Saying "just fix it" instead of using /debug
Asking Claude to fix an error without diagnosing it first leads to Claude guessing. Sometimes it guesses right. Often it changes the wrong thing and creates a new problem. Run /debug first , it reads the error, finds the root cause, and plans a fix before touching anything.
🚫 Still using --dangerously-skip-permissions
This was always a last resort and now there's no reason to use it. Auto Mode (Team/Enterprise/API plans) gives you the same uninterrupted workflow with a classifier blocking dangerous actions. If you're on Pro or Max, use Accept Edits mode instead.
🚫 Letting CLAUDE.md grow too big before archiving
The file size check in the Morning Kick-Off prompt exists for a reason. When CLAUDE.md gets over 30k characters, Claude's performance on that project noticeably degrades , it starts drifting from the rules and missing context. Archive early, not when it's already causing problems.
🚫 Never adding to Project-Specific Rules
If you correct Claude doing the same thing twice, that's a rule waiting to be written. The Project-Specific Rules section is supposed to grow. Every time you find yourself saying "no, we do it this way" , add it. A CLAUDE.md that never grows is one that never gets better.
🚫 Installing skills but never invoking them
Skills don't run themselves unless you either call them or reference them in CLAUDE.md rules. If you've installed /simplify and /debug but never type them or tell Claude to use them automatically, they're doing nothing. Add them to your Project-Specific Rules so Claude uses them without being asked.
🚫 Skipping the Wrap-Up prompt
The Wrap-Up prompt isn't just about saving , it updates the Session Log, captures what was done, and sets up the next session. If you skip it, the next Kick-Off starts with stale context and Claude has to work harder to understand where things stand. It takes 30 seconds and saves minutes of re-explaining.
🚫 Working on main branch for everything
Claude should create a branch any time it's working on something that might break existing functionality , your CLAUDE.md rules say so. But if you don't check what branch you're on at Kick-Off, you might not notice when Claude skips this. The Kick-Off prompt runs git status and git log for exactly this reason.

Troubleshooting

❌ Claude Code not installing
If the native installer fails, use the npm fallback: npm install -g @anthropic-ai/claude-code && claude. If still failing, check your internet connection or restart the Repl.
❌ Git push failing
Make sure GitHub is connected in Replit Settings → Connected Services. Check you have write access to the repo.
❌ CLAUDE.md not being read
The file must be named exactly CLAUDE.md (case-sensitive) in the project root, not a subfolder.
❌ Claude forgetting rules mid-session
Your CLAUDE.md is probably too large. Use the Kick-Off prompt to check file size and archive old logs if needed.
❌ Changes not showing on GitHub
Run git status to check for uncommitted changes, then git add ., git commit -m "message", and git push.
❌ Auto Mode not available
Auto mode requires Team, Enterprise, API, or Max plan (Max requires Opus 4.7 or 4.8). Not available on Pro. Also available on Bedrock, Vertex, and Foundry as of May 30, 2026, opt in with CLAUDE_CODE_ENABLE_AUTO_MODE=1.
